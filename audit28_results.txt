FINDING #2 — Race Condition: Boss GLB Not Loaded → bossActive Stuck
────────────────────────────────────────────────────────────────────────────────
Lines: 4517-4543 (createBossEnemy)
Category: Boss Edge Cases / Race Conditions

When `createBossEnemy()` is called, it synchronously checks
`state.loadedModels[bossKey]`. If the boss GLB hasn't finished loading yet
(it loads async in batches via `preloadEnemyModel`), the procedural fallback
box is used — that's fine. But the real issue is that `c.bossActive = true`
is set on line ~7248 BEFORE calling `createBossEnemy()`. If the boss spawns
at extreme range and is immediately cleaned up by a distance check or the
player exits gunner mode, `c.bossActive` is set to false ONLY inside the
kill handler (line 7167). There's no cleanup in `exitGunnerMode` that resets
`c.bossActive`, so if the player presses Escape or dies during a boss fight,
`c.bossActive` remains `true` forever, and no more bosses will ever spawn.

Old code (lines 3957-3966, exitGunnerMode):

  c.enemies.forEach(e => { if (e && e.group) { scene.remove(e.group); disposeObject(e.group); } }); c.enemies = [];

New code:
function exitGunnerMode(skipScreenChange) {
  c.active = false;
  c.bossActive = false;
  mouseHeld = false;
  if (document.pointerLockElement) document.exitPointerLock();

Why it matters: Without this, any death during a boss fight permanently
prevents future boss spawns for the entire session, silently breaking 20-kill

FINDING #3 — Skill XP Overflow: gainSkillXP Has No Maximum Level Guard
────────────────────────────────────────────────────────────────────────────────
Lines: ~1357-1367 (gainSkillXP function)
Category: Skill System Bugs

The `gainSkillXP` function calls `getSkillCeiling` to determine the XP
needed to level up, but there's no maximum level check. `getSkillCeiling`
uses `Math.pow` which grows exponentially, but the `getSkillBonus` function
on line ~1370 returns `1 + skill.level * 0.1`, meaning at extreme levels
the bonus becomes absurdly high (e.g., level 100 = 11x multiplier). This
lets hacking skill give 70% loot drop chance (the 0.7 cap saves us there),
but gunnery/piloting/engineering bonuses are uncapped.

Need to verify exact line numbers — let me check:

Old code (gainSkillXP, approximately line 1360):
function gainSkillXP(skillName, amount) {
  const skill = state.skills[skillName];
  if (!skill) return;
  const rate = getSkillRate(skillName);
  skill.xp += amount * rate;
  const ceiling = getSkillCeiling(skill.level);
  if (skill.xp >= ceiling) {
    skill.xp -= ceiling;
    skill.level++;
    addComms('Skills', `${skillName} leveled up to ${skill.level}!`);
  }
}

New code:
function gainSkillXP(skillName, amount) {
  const skill = state.skills[skillName];
  if (!skill) return;
  if (skill.level >= 50) return; // Max level cap
  const rate = getSkillRate(skillName);
  skill.xp += amount * rate;
  const ceiling = getSkillCeiling(skill.level);
  if (skill.xp >= ceiling) {
    skill.xp -= ceiling;
    skill.level = Math.min(50, skill.level + 1);
    addComms('Skills', `${skillName} leveled up to ${skill.level}!`);
  }
}

Why it matters: Without a level cap, long-running sessions accumulate
ridiculously high skill bonuses. At level 50 the bonus is 6x which is
already powerful. The XP ceiling growth slows progression but doesn't stop
it, and players who exploit auto-mine/auto-target can AFK to absurd levels.

FINDING #5 — Skin applySkin Mutates Shared Materials
────────────────────────────────────────────────────────────────────────────────
Lines: 6307-6316 (applySkin)
Category: Cosmetics / Skins

`applySkin` traverses the ship and directly modifies `child.material.color`,
`roughness`, `metalness`, and `emissive` — but it never clones the material
first. If the ship uses GLB models loaded via `reskinModel`, those materials
come from a shared `_materialCache` (line ~4209). Mutating cached materials
means ALL enemies/NPCs using the same base material from that GLB will also
change appearance when the player applies a skin.

Old code (lines 6307-6316):
function applySkin(skin) {
  state.currentSkin = skin;
  ship.traverse(child => {
    if (!child.isMesh || !child.material || child.material.isMeshBasicMaterial) return;
    // Determine if this is hull or accent based on original color
    const isAccent = child.material.emissiveIntensity > 0.2;
    child.material.color.setHex(isAccent ? skin.accent : skin.primary);
    child.material.roughness = skin.roughness;
    child.material.metalness = skin.metalness;
    if (child.material.emissive) child.material.emissive.setHex(skin.emissive);
  });

New code:
function applySkin(skin) {
  state.currentSkin = skin;
  ship.traverse(child => {
    if (!child.isMesh || !child.material || child.material.isMeshBasicMaterial) return;
    // Clone material to avoid mutating shared/cached materials
    if (child.material._pooled || child.material._shared) {
      child.material = child.material.clone();
    }
    const isAccent = child.material.emissiveIntensity > 0.2;
    child.material.color.setHex(isAccent ? skin.accent : skin.primary);
    child.material.roughness = skin.roughness;
    child.material.metalness = skin.metalness;
    if (child.material.emissive) child.material.emissive.setHex(skin.emissive);
  });

Why it matters: Applying a skin can visually corrupt all enemies/NPCs using
the same base GLB material. This is a subtle but noticeable visual glitch
where applying "Blood Storm" skin could turn all fighters red too.

New code:
canvas3d.addEventListener('webglcontextrestored', () => {
  console.log('[Old Eden] WebGL context restored');
  const lostDiv = document.getElementById('webgl-lost-overlay');
  if (lostDiv) lostDiv.classList.remove('active');
  // Re-init renderer settings
  renderer.setPixelRatio(Math.min(window.devicePixelRatio, 1.5));
  renderer.toneMapping = THREE.ACESFilmicToneMapping;
  renderer.toneMappingExposure = 1.8;

FINDING #7 — Pointer Lock: requestPointerLock Inside Gesture May Reject
────────────────────────────────────────────────────────────────────────────────
Lines: 6618 (T key chatbot toggle re-locks)
Category: Pointer Lock Edge Cases

When closing the chatbot panel with 'T' key (line 6618):
```
canvas3d.requestPointerLock();
```
This call is inside a `keydown` event handler, which counts as a user
gesture. HOWEVER, the user just typed 'T' in the chatbot input. The browser
may still have focus on the chatbot input element. Some browsers reject
`requestPointerLock()` if the triggering element is not the lock target or
if the document hasn't had a recent mouse click. The rejected promise is
unhandled.

Old code (lines 6614-6619):
    if (state.chatbot.visible) {
      if (document.pointerLockElement) document.exitPointerLock();
      setTimeout(() => chatInput.focus(), 100);
    } else {
      canvas3d.requestPointerLock();
    }

New code:
    if (state.chatbot.visible) {
      if (document.pointerLockElement) document.exitPointerLock();
      setTimeout(() => chatInput.focus(), 100);
    } else {
      try { canvas3d.requestPointerLock()?.catch(() => {}); } catch(_) {}
    }

Why it matters: Unhandled promise rejection on `requestPointerLock()` can
log console errors and, on some browsers, trigger the "pointer lock was
rejected" modal warning. Silencing the rejection is safe because the user
will see the lock-prompt overlay and can click to re-lock.

FINDING #11 — Race: NPC Auto-fill setTimeout Uses Stale `_orderId`
────────────────────────────────────────────────────────────────────────────────
Lines: 6159-6184 (_placeOrder NPC auto-fill)
Category: Race Conditions

`_placeOrder` creates a player order, then sets a `setTimeout(2000-5000ms)`
to auto-fill it against NPC orders. The timeout captures `_orderId` in
closure. If the player clicks "Place Order" rapidly, multiple timeouts fire
with different `_orderId` values that may reference orders already consumed
by earlier timeouts. Specifically:

1. Player places sell order at T=0 → orderId "player-1000"
2. Player places another sell order at T=100 → orderId "player-1100"
3. At T=3000, first timeout fires, fills "player-1000" against NPC buys
4. The NPC buy orders are now depleted
5. At T=3100, second timeout fires, finds no NPC matches → no fill

This is actually benign (no corruption). BUT: The real bug is on line 6173:
when `_ord.type === 'buy'` and NPC fills it, the code gives the player items
but the player already paid `price * qty` upfront (line 6158). The NPC fill
uses `_ord.price * fq` as the sell price — but the player already prepaid.
This is correct for buy orders (prepaid). However for SELL orders: the player
already removed items from inventory (line 6153-6155), and on fill they get
`state.player.credits += _ord.price * fq`. This is also correct.

Actually the race condition is: between the player placing a buy order
(credits deducted) and the NPC auto-fill (items delivered), the player could
rebirth or die, clearing their inventory. The items get added to
`state.inventory` which was already cleared by rebirth. The credits were
already deducted from the OLD credit balance. Net effect: player loses
credits and gains phantom items in a new life.

Old code (line 6157-6158):
  if (type === 'buy') { state.player.credits -= price * qty; }
  const _orderId = 'player-' + Date.now();

New code:
  if (type === 'buy') { state.player.credits -= price * qty; }
  const _orderId = 'player-' + Date.now();
  const _orderRebirthNum = state.player.rebirths; // snapshot rebirth count

And in the setTimeout (around line 6163):
Old:
  setTimeout(() => {
    const _ord = state.market.orders.find(o => o.id === _orderId);
    if (!_ord || _ord.quantity <= 0) return;

New:
  setTimeout(() => {
    // Abort if player rebirthed since order was placed
    if (state.player.rebirths !== _orderRebirthNum) return;
    const _ord = state.market.orders.find(o => o.id === _orderId);
    if (!_ord || _ord.quantity <= 0) return;

Why it matters: Without the rebirth guard, NPC auto-fill can deliver items
to a new life that the OLD life paid for. This is a minor exploit but breaks
the "death costs everything" design pillar.

FINDING #12 — Ghost NPC Material Clone Leak: Every Ghost Clones Per Mesh
────────────────────────────────────────────────────────────────────────────────
Lines: 5901-5911 (spawnSystemNPCs ghost material cloning)
Category: Performance / Memory

When spawning a ghost NPC from past lives, the code clones EVERY mesh's
material individually:
```

    if (child.isMesh && child.material) {
      child.material = child.material.clone();
      child.material.emissive = new THREE.Color(0x6688ff);
      ...
    }
});
```

If the NPC uses a GLB model with 20+ meshes, this creates 20+ new material
instances that are never added to `_materialCache` and are never explicitly
disposed when the NPC is removed (they're removed via `disposeObject`).
Meanwhile, the `disposeObject` function traverses and disposes geometries
and materials — so disposal IS handled. But the real issue is: these cloned
materials bypass the material cache, defeating the purpose of
`_getCachedMaterial`. Each system jump creates new ghost NPCs with new
material clones.

This is a minor performance concern but not a critical bug. The memory leak
is bounded by `spawnSystemNPCs` which disposes old NPCs before creating new
ones. The per-clone overhead is small. Noting for completeness.

More importantly: the ghost tint code uses `new THREE.Color(0x6688ff)` on
line 5906, which allocates a new Color object per mesh. Should be cached.

Old code (lines 5901-5911):
      lastNpc.group.traverse(child => {
        if (child.isMesh && child.material) {
          child.material = child.material.clone();
          child.material.emissive = new THREE.Color(0x6688ff);
          child.material.emissiveIntensity = 0.6;
          child.material.transparent = true;
          child.material.opacity = 0.7;
          child.material.depthWrite = false;
        }
      });

New code:
      const _ghostEmissive = new THREE.Color(0x6688ff);
      lastNpc.group.traverse(child => {
        if (child.isMesh && child.material) {
          child.material = child.material.clone();
          child.material.emissive = _ghostEmissive;
          child.material.emissiveIntensity = 0.6;
          child.material.transparent = true;
          child.material.opacity = 0.7;
          child.material.depthWrite = false;
        }
      });

Why it matters: Minor—saves one Color allocation per mesh. The shared Color
is safe because all ghost materials use the same emissive value.

FINDING #13 — Enemy shootRate Scaling Can Go Below Zero
────────────────────────────────────────────────────────────────────────────────
Lines: ~4300 (createEnemy push)

      const fireInterval = e.isBoss ? Math.max(800, 1500 * (1 - (c.cycle - 1) * 0.03)) : (e.shootRate || 3000);

Why it matters: Boss fights should get harder with cycle progression, not
stay static while regular enemies ramp up. At cycle 20, regular enemies fire
at 1000ms while bosses still fire at 1500ms — bosses feel like a downgrade.

FINDING #14 — Rebirth Resonance: Speed Bonus Applied to maxSpeed Not Clamped
────────────────────────────────────────────────────────────────────────────────
Lines: 5058 and 2008 (both rebirth paths)
Category: Rebirth Milestones / Balancing

Both rebirth handlers apply speed resonance bonus:
```
state.flight.maxSpeed = 120 * (1 + (r.speed || 0) / 100);
```

The resonance `speed` bonus is capped at 50 per the fuseFragments function
(`Math.min(50, ...)`), so max speed can reach `120 * 1.5 = 180`. This is
fine. But then `applyUpgrades()` is called, which applies `engineSpeed`
multiplier. After reset, `engineSpeed = 1`, so `maxSpd = 180 * 1 = 180`.

But later when the player buys Engine Overcharge (1.3x), `engineSpeed` goes
to 1.3. In the game loop, maxSpeed is calculated as:
```

```

With afterburner (2.5x), Engine Overcharge (1.3x), speed resonance (1.5x on
maxSpeed), and genome speed mult (up to ~1.3x at 255 genome), that's:
`180 * 2.5 * 1.3 * 1.3 * 1 = 760.5` units/sec.

This isn't necessarily a bug — high speed is fun. But there's NO physics
collision at this speed (asteroid collision checks use distance which may
skip over asteroids entirely between frames). At 760 u/s with dt=0.016,
the ship moves 12.2 units per frame — asteroids with radius ~4 could be
entirely skipped.

Old code (game loop asteroid collision, around line 7269):
      const dist = a.position.distanceTo(ship.position);
      const mesh = a.children && a.children[0];
      const radius = (mesh && mesh.geometry && mesh.geometry.boundingSphere && mesh.geometry.boundingSphere.radius) || 4;
      if (dist < radius + 3) {

New code:
      // Use swept-sphere check to prevent tunneling at high speeds
      const dist = a.position.distanceTo(ship.position);
      const mesh = a.children && a.children[0];
      const radius = (mesh && mesh.geometry && mesh.geometry.boundingSphere && mesh.geometry.boundingSphere.radius) || 4;
      const effectiveRadius = radius + 3 + fl.speed * dt; // expand by movement distance
      if (dist < effectiveRadius) {

Why it matters: At high speed (afterburner + resonance + upgrades), the
player can fly through asteroids without taking damage because the per-frame
position delta exceeds asteroid collision radius. Adding `fl.speed * dt`
to the collision check radius is a simple swept-sphere approximation.
